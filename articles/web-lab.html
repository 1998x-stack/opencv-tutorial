阶段四 · 实验室

交互式实验室

前面几篇文章都在讲算法本身；本文解释承载它们的那个本地网页。它用一条 HTTP 端点把共享管线暴露给浏览器，让"结果图 / 中间阶段 / 参考误差"可以在同一次请求里被观察——同时把上传限制、离线绑定与隐私边界讲清楚。

01 · 为什么算法文章之外还要一个“实验室”

读算法文章时，参数只能靠想象：σ 从 1.2 调到 2.0，输出现场是什么样？Canny 的两个阈值改变后会多出多少条边？更关键的是，文章里说的“参考实现与 OpenCV 一致”，读者无法当场验证。把管线做成一个可点击的观察台，就是让这些问题有即时反馈，而不是让读者盲信文字。

实验室的设计目标有三条，且都对应仓库里可检查的实现：参数可调且结果即时回传、中间产物与最终结果并列可见、与参考实现的差异被量化显示。它不是一个新算法，而是把 pipeline.py 已经返回的 stages 与 metrics 直接渲染出来。

02 · 核心机制：一个进程，一个端点

实验室由标准库的 ThreadingHTTPServer 提供，不依赖任何 Web 框架，也不需要联网。启动方式与 CLI 一致：

python -m opencv_tutorial serve --host 127.0.0.1 --port 8765
# OpenCV Lab at http://127.0.0.1:8765

服务端只定义少量端点，每个端点都只做一件可预期的事：

实验室 HTTP 端点
方法 / 路径返回用途
GET /api/health{status, opencv}存活检查与 OpenCV 版本
GET /api/catalogALGORITHMS 字典侧边栏的算法列表与描述
GET /api/curriculumget_curriculum()24 周课程网格
GET /api/sample{image} data URL确定性的合成样本图
POST /api/process{images, metrics}运行一个算法并回传全部阶段
GET / /style.css /app.js静态文件白名单内的前端资源

关键的一点是：网页并没有自己的算法实现。侧边栏算法列表直接来自 pipeline.py 的 ALGORITHMS，处理请求直接调用同一个 run_pipeline。因此 CLI、基准测试与网页三者在语义上不会漂移——修好一处，三处一起变。

用 FastAPI/Flask 等框架重写这段服务并不改变算法结论；它反过来会增加依赖面，与“离线优先”的目标相冲。因此这里选择标准库，代价是需要自己处理请求上限与错误分支（见第 05 节）。

03 · 数据流：图片怎么跨过进程边界

网页与算法在不同的进程里，图片必须被序列化成文本。浏览器用 readAsDataURL 把上传文件读成 data:image/png;base64,… 形式的字符串，连同参数一起放进 JSON；服务端则按相反顺序还原：

解码：五道检查，任何一道不过就拒绝

  1. 载荷必须是字符串，且长度不超过 2 × MAX_REQUEST；
  2. 若带 data: 前缀，必须包含 ;base64,；
  3. base64.b64decode(validate=True) 严格解码，非法字符直接报错；
  4. 解码后的字节数不超过 MAX_REQUEST（8 MiB）；
  5. cv2.imdecode 必须能成功，且像素数不超过 8 000 000。

这五道检查都对应一个具体的失败原因，而不是笼统的“上传失败”。任何一步驳回，服务端回 400 并在 error 字段里给出原因（截断到 300 字符）。

编码：PNG data URL + 指标

管线把每个阶段图用 cv2.imencode(".png", …) 压成 PNG，再转成 data URL。响应形如 {"images": {name: dataURL}, "metrics": {…}}。因为 metrics 里只有普通数字、字符串与整数，序列化时用 allow_nan=False 可以把 NaN/Infinity 直接变成报错，避免前端静默拿到非法值。

04 · 离线与隐私：默认只在本机

服务默认绑定 127.0.0.1:8765，而不是 0.0.0.0。这意味着同一局域网内的其他机器默认也访问不到它；serve(host, port) 的两个参数只在显式传入时才会改变这一点。

  • 无外部依赖算法在本地由 NumPy 与 OpenCV 执行；页面不请求任何 CDN、字体或分析脚本，断网可用。
  • 不持久化上传上传的图片只在内存中解码与处理，不以文件形式写入磁盘；关闭进程即消失。
  • 响应不可缓存JSON 响应带 Cache-Control: no-store，避免处理结果被浏览器或中间层缓存。
  • 资源白名单静态文件只提供 /、/style.css、/app.js 三项，其余路径一律 404，不提供目录遍历。
  • 嗅探防护所有响应带 X-Content-Type-Options: nosniff。

这是本地学习工具，不是面向公网的加固服务。仓库明确声明：未经鉴权、限流、隔离与运维审查，不要把它绑定到公网接口。本文讨论的所有“安全边界”都以本机模型为前提。

05 · 边界与失败模式

自建 HTTP 服务意味着逐个显式处理失败分支。下面是这段代码里真实存在的拒绝条件，以及它们各自对应的状态码：

条件状态码原因
请求长度 <1 或 >8 MiB413请求过大或为空
Content-Type 不是 application/json415不支持的媒体类型
JSON 不是对象 / 解码失败400请求体非法
图片非法或超过 8 MP400解码或尺寸校验失败
未知路径404不在白名单内

还有两个容易被忽略的行为。其一，上传文件大小在浏览器侧就有一道预检：非图片类型与超过 5 MB 的文件不会发请求，直接提示。其二，参考一致性检查只在小图上执行：当灰度图不超过 400 000 像素时，管线才会调用 NumPy 参考实现并记录 reference_mae 等指标；大图下这些字段缺失，前端显示 N/A。因此 elapsed_ms 在某些算法上包含了可选的参考对比，它不是纯 OpenCV 优化后的耗时（参见 docs/testing.md 的已知限制）。

最后一个边界属于设计本身：一次请求只运行一个算法。想要对比两种算法，需要发两次请求，或者在文章里看各自的中间产物。这保持了请求的确定性，代价是前端不提供“多算法并行对比”。

可运行验证

上面这些端点和边界不是口头约定，而是被集成测试真实调用的。测试会在一个临时端口上启动 LabHandler，依次请求健康检查、课程表和首页，再 POST 一张编码后的合成图：

with urlopen(live + "/api/health") as r:
    assert json.load(r)["status"] == "ok"
with urlopen(live + "/api/curriculum") as r:
    assert len(json.load(r)) == 24
with urlopen(live + "/") as r:
    assert b"VISION" in r.read()

image = encode_image(make_sample(160, 128))
req = Request(live + "/api/process",
              json.dumps({"image": image, "algorithm": "otsu"}).encode(),
              {"Content-Type": "application/json"}, method="POST")
with urlopen(req) as r:
    assert json.load(r)["metrics"]["algorithm"] == "otsu"

编码/解码的往返同样被断言：np.testing.assert_array_equal(decode_image(encode_image(original)), original)，而非法 payload（"data:image/png;base64,not-valid"）必须抛出 ValueError。运行方式：pytest tests/test_server_and_motion.py -k "roundtrip or http_endpoints"。测试用 ThreadingHTTPServer(("127.0.0.1", 0), LabHandler) 绑定 0 号端口，因此不会占用文档里写的固定 8765，也不会与本地在跑的服务冲突。

06 · 观察什么：三个读数对应三类问题

全面板右侧只展示三个读数，它们分别回答三个不同层面的问题，而不是堆砌所有指标：

读数字段回答的问题
执行时间elapsed_ms这次处理花了多久（毫秒）
图像分辨率width × height处理的是多大的图（来自灰度图）
参考检查见下与 OpenCV/参考实现的差异是多少

“参考检查”具体显示哪个字段，取决于当前算法：高斯用 reference_mae（与 cv2.GaussianBlur 的平均绝对误差），Sobel 用 gradient_max_error（与手写水平梯度的最大误差），Otsu 用 reference_pixel_difference（与 cv2.threshold(THRESH_OTSU) 不一致的像素数）与 selected_threshold（选中的阈值）。其余算法没有参考实现，显示“N/A”。

读取这些数时不要把“小”直接当成“快”：参考对比本身在计时区间内，所以当 reference_mae 出现时，elapsed_ms 会偏高。要比较算法真实速度，请用 python -m opencv_tutorial benchmark，它复用相同输入并报告中位数与 P95。
